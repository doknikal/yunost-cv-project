# Доказательства для components-v2

Основное описание: [EDGE_METHOD.md](../../EDGE_METHOD.md). Этот каталог отделён от
старого OCR-исследования и исторических CSV. Новые измерения не импортировались в SQLite.

## Что сохранено

- `manual_staircase.json`: 18 строк области разработки, визуальная неопределённость ±3 px.
- `manual_scan.json`: 16 отложенных строк скана, ±5 px.
- `manual_photo.json`: 19 отложенных строк фото, ±5 px.
- `development-v2.json`, `held-out-v2.json`: сопоставления, ошибки каждого края,
  несовпавшие строки, предсказанные координаты, значения SD и хеши кода/разметки.
- Соответствующие PNG: зелёные рамки предсказанных строк, пурпурные отметки визуальных
  эталонных краёв. Это результаты проверки, а не источник разметки.
- `synthetic-v2.json`: точная синтетика с короткими строками и далёкой пылью.
- `ocr-preservation-json-v2.json`: сравнение сохранённых **сериализованных JSON** ответов
  на оригинальной пользовательской странице, контроль исторических хешей.
- `legacy-default-compatibility-v2.json`: все девять признаков на всех 111 PNG совпали
  со старым `HEAD:cvpipe.py` при неизменённом вызове по умолчанию; NaN сопоставлен с NaN.
  Сравнение шло в памяти, исходные CSV не перезаписывались.
- `user-page-browser-v2.png`: composite настоящих слоёв браузера после реального OCR-запроса;
  не полноценный скриншот страницы и не ручная оценка всех показанных строк.

Разметки сделаны визуально моделью до просмотра предсказаний. Они **не человеческий
gold standard**. Подсказки текста в разметке не оценивают OCR-транскрипцию. Небольшое
различие inclusive/half-open края меньше заявленной визуальной неопределённости.
Отложенные данные не использовались для последующей настройки компонентов.

## Как читать результаты

На чистой «лесенке» оба финальных метода находят 18 строк. Число 14 относилось
к раннему прототипу v2, который объединял строки по перекрытию чернил; это **не**
финальный результат legacy. Переход к центрам знаков устранил эту ошибку разработки.

На фото оба метода выдают 19 предсказаний, но по вертикальным соответствиям legacy
получает 17/19, v2 — 19/19. При этом у v2 есть две большие ошибки края (22 и 15 px,
строки 13 и 14 по нумерации от единицы). Компоненты касающихся соседних строк остаются
источником ошибки. Их не исправляли по отложенным ответам и не скрывали из средней ошибки.
MAE legacy вычислена по другому, меньшему набору совпавших строк: сравнивать её без полноты
нельзя. Ни один общий SD не заменяет проверку отдельных строк.

Это проверка **заданных одноколоночных областей**. Здесь нет доказательства точности
автоматического поиска колонок, рамок и рисунков на всём корпусе. Положительная проверка
старого вызова на 111 страницах доказывает совместимость, а не правильность старой метрики.

## Воспроизведение

Из корня репозитория, с установленными `requirements.txt`:

```bash
.venv/bin/python docs/edge_evaluation/evaluate_edges.py --split development \
  --output .venv/evaluation/edges/repeat-development.json
.venv/bin/python docs/edge_evaluation/evaluate_edges.py --split held_out \
  --output .venv/evaluation/edges/repeat-held-out.json
TESSDATA_PREFIX="$PWD/tessdata" .venv/bin/python -m pytest tests/ -q
```

Существующие JSON/PNG не перезаписываются: для нового прогона нужен новый путь.
`prep_package.py` для этой проверки не запускать: он регенерирует исторические входы.
При изменении алгоритма этот отложенный набор становится регрессионным; для нового
независимого утверждения потребуется новая разметка и новый отложенный номер.

Дальнейшая проверка должна охватить смешанную вёрстку, рамки и кривые фотографии,
в том числе `1957-10_p05`, `1963-12_p06`, `1965-02_p09`, с отдельной разметкой
регионов и физических строк, вторым проверяющим и разбиением по номерам. Жанровые
метки и желаемая историческая тенденция не должны служить целевой величиной края.
